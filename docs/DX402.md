# DX402 — Durable Evidence for x402

**Extension key:** `durable-evidence`
**Spec:** [`docs/plans/dx402/02-SPEC-v0.1.md`](plans/dx402/02-SPEC-v0.1.md)
**Research and prior art:** [`docs/plans/dx402/00-RESEARCH.md`](plans/dx402/00-RESEARCH.md)

---

## The problem

x402 settles payment on-chain permanently, then delivers the purchased resource
**exactly once**, in the body of a `200 OK`, and keeps nothing.

If the buyer did not capture that body at that instant, it is gone. Neither party
can later prove *what* was delivered — only *that* payment happened. There is no
artifact to bring to a dispute.

This is not our observation alone. *Five Attacks on x402 Agentic Payment
Protocol* states it plainly:

> "the HTTP response has already been sent, so RR cannot claw the resource back"

Delivery is irreversible; settlement is reversible. The paper does not propose a
fix and explicitly does not cover non-repudiation or disputes.

## What DX402 does

Three properties, in order of importance:

1. **Durable** — the delivered body survives the session.
2. **Private** — encrypted to the payer. Not the facilitator, not the storage
   backend, not us.
3. **Coupled** — no registration and no extra round trip.

## The idea

> A payment authorization is a digital signature. A digital signature yields the
> signer's **public key**, not merely their address. So the resource server can
> encrypt to the payer using key material the payment already produced.

**Paying is publishing your encryption key.**

| Family | Curve | Where the payer's key comes from |
|---|---|---|
| EVM | secp256k1 | ECDSA recovery over the EIP-712 digest |
| Solana / Fogo | ed25519 | the address **is** the key |
| NEAR | ed25519 | access key (`ed25519:…`) |
| Stellar | ed25519 | the `G…` address is the encoded key |
| Algorand | ed25519 | address is key + 4-byte checksum |
| Sui | either | address is a hash; the signature carries the key |
| XRPL | either | `SigningPubKey` of the signed transaction |

Four of seven need nothing but the address.

## Where each piece runs

The facilitator is **not** in the response path — it only handles `/verify` and
`/settle`, and never sees a body. So the work splits:

```
                    ┌──────── SELLER (x402-axum) ────────────┐
Client ─GET+PAY──►  │ handler → BODY                          │
                    │  1. CEK → AES-256-GCM(body)             │
                    │  2. recover payer key from the payment  │
                    │  3. ECIES(CEK → payer key)              │
                    │  4. write ciphertext → sink             │
                    └───────────────┬─────────────────────────┘
                                    │ POST /dx402/anchor  (metadata only)
                                    ▼
                    ┌──── FACILITATOR (x402-rs) ──────────────┐
                    │ notary: signs an EIP-712 EvidenceReceipt│
                    │ index:  paymentId → pointer + hash      │
                    │ never holds plaintext or keys (direct)  │
                    └───────────────┬─────────────────────────┘
Client ◄─ 200 + BODY + X-Payment-Response + X-Durable-Evidence
```

## Seller integration

```rust
use std::sync::Arc;
use x402_axum::durable::{DurableConfig, DurableEvidenceHook, HttpPutSink};

let hook = DurableEvidenceHook::new(
    DurableConfig::from_env(),                             // direct mode, 90d, 32 MiB cap
    Arc::new(HttpPutSink::new("https://evidence.example.com")),
    "https://facilitator.ultravioletadao.xyz",
);

let layer = x402
    .with_price_tag(usdc.amount(0.01)?)
    .with_durable_evidence(hook);
```

That is the whole integration. Evidence is produced after settlement, and
**nothing here can fail a payment** — an oversized body, a full memory budget, an
unreachable sink, or a smart-contract wallet with no recoverable key all
downgrade to a skip notice in the header while the response is delivered exactly
as before.

### Seller size limits

Sealing buffers the body: the plaintext, the ciphertext, and the copies in
between. Two settings bound that, and **they only work as a pair** — a generous
body limit with unbounded concurrency is not a bigger product, it is an OOM, and
an OOM drops responses that were already paid for.

| Variable | Default | Notes |
|---|---|---|
| `DX402_MAX_BODY_BYTES` | `33554432` (32 MiB) | Largest body that gets evidence. Above it: `{"skipped":"too_large"}`, body delivered in full |
| `DX402_MAX_INFLIGHT_BYTES` | `167772160` (160 MiB) | Memory all concurrent captures may hold at once. Exhausted: `{"skipped":"busy"}`, body delivered in full |

Read by `DurableConfig::from_env()`; a value that does not parse is ignored in
favour of the default and logged. The floor is 16 KiB, so `=0` cannot silently
skip everything, and the body limit is clamped to what the budget can afford, so
a mismatched pair reports an honest `too_large` instead of `busy` forever.

The budget is **not memory the process takes, it is memory it refuses to
exceed**: reservations are sized from each body, so a seller returning 4 KB of
JSON never holds more than a few KB however high the ceiling sits. It costs
nothing until large bodies actually flow, which is why it is the generous half
of the pair and the body limit is the conservative one.

It is denominated in bytes of real memory and charges each capture
roughly **four times** the body — an estimate, not a profile. A body that
announces its length reserves that length; one that does not (a streaming
handler) has to reserve the worst case. The reservation is refused, never
queued: buffering happens before the buyer's response goes out, so waiting for
memory would delay a delivery that has already been settled.

**32 MiB is not a storage ceiling**, and it is not our storage either. S3 takes
5 GiB in a single `PUT`, and in pointer mode — what the `x402-axum` hook does —
the object lands in **the seller's own sink**. The facilitator's bucket only ever
receives the inline `sealed` path, which the 64 KiB request limit caps at ~47 KB.
Raising this number does not grow the facilitator's storage.

Why 32 MiB and not more: this is the default a seller gets for **not** thinking
about it, in a process whose memory we do not size. The only measured case that
DX402 ever refused was an 18 MB response, so the default has to clear that — and
past that, the smallest number that clears it with room beats the largest one our
own infrastructure could absorb. Raising it is one variable; lowering it after
integrators have built on a bigger promise is a regression. For objects genuinely
too large to hold in memory the answer is streaming
(`docs/plans/dx402/04-STREAMING-EVIDENCE-HANDOFF.md`, phase 1), not a larger
number here.

## Buyer integration

> **The easiest chain for the seller can be the impossible one for the buyer.**
>
> On ed25519 chains the address *is* the public key, so sealing is trivial. But
> decrypting needs the raw 32-byte private key, and a wallet held in **custody**
> signs without exposing ECDH — so a custodial buyer cannot open their own
> evidence. Check that the buyer controls its key directly before recommending a
> chain on the strength of how easy sealing is. (Raised by KarmaKadabra,
> 2026-08-17, from a Solana fleet on Paybox custody.)

```rust
use x402_reqwest::durable::{evidence_of, recover};

let evidence = evidence_of(response.headers())?;      // parse X-Durable-Evidence
let body = recover(&client, &evidence, &my_secret_key).await?;
```

`recover` verifies `contentHash` against the decrypted bytes. That check is what
catches a seller that anchored something other than what it served, so it is not
optional.

## Anchoring: prove the anchor is yours

An anchor carrying a valid **payee signature** is `verified` and final. One
without is **provisional**: it still blocks a duplicate, but a verified anchor for
the same payment supersedes it.

That asymmetry exists because the `paymentId` claim is permanent. Without it,
whoever anchored first owned the evidence of a payment forever and the real seller
was locked out — reproduced against production by KarmaKadabra, 2026-08-18.

The signature check is **not** behind `DX402_REQUIRE_PROOF`. That flag phases in
the on-chain half, which needs an RPC and cannot run on every family. A signature
needs neither, so it is enforced from day one.

The SDKs build the digest for you — do not hand-roll the EIP-712:

```python
from uvd_x402_sdk.dx402 import sign_anchor_ed25519, sign_anchor_evm

# Solana / Stellar payee
sig = sign_anchor_ed25519(seed, payment_id, content_hash)

# EVM payee (must be the address that got paid)
sig = sign_anchor_evm(priv, payment_id, content_hash, pointer, payee, chain_id)
```

```ts
import { signAnchorEd25519, signAnchorEvm } from 'uvd-x402-sdk';
```

Then send it as `sellerSignature` on the anchor.

Under the hood it signs `Dx402AnchorAuthorization { paymentId, contentHash,
pointer, payee }` under domain `{name: "DX402 Anchor", version: "1", chainId}`:

- **EVM payee** → EIP-712 signature, `payee` set to your address.
- **Solana / Stellar payee** → raw **ed25519** signature over the same digest,
  with `payee` as the zero address. An ed25519 address does not fit the `address`
  field, and the binding is already established by which key verifies.
- `pointer` is whatever you supplied, or the empty string when you send `sealed`
  and the facilitator issues the pointer — you cannot sign a value you have not
  seen.

> **`chainId` is 0 on non-EVM chains.** It comes from parsing the network's
> CAIP-2 identifier, and only `eip155:` yields a number — everything else falls
> through to 0. Correct, but nobody guesses it, and a wrong `chainId` produces a
> signature that verifies against nothing with no error anywhere. The SDK helpers
> handle it; this is here for whoever has to debug a signature that will not
> verify. (Raised by KarmaKadabra, 2026-08-18.)

> **A custodial payment wallet does not stop you being a recipient.** The
> seller's *encryption* key is not its *payment* key and should not be: generate
> a plain local keypair used only to decrypt evidence — no funds, no gas, no
> custodian involved — and list its public key as the `seller` recipient. Only
> **signing the anchor** needs the payee's own key, because that signature is the
> claim.

> **Solana blockhash**: request it with `finalized`, not `confirmed`. The
> facilitator's node is a different one and may not have seen a `confirmed`
> blockhash yet, which surfaces as `Blockhash not found` at settle time.

## Facilitator configuration

All optional. **DX402 is off unless `ENABLE_DX402=true`.**

| Variable | Default | Notes |
|---|---|---|
| `ENABLE_DX402` | `false` | master switch |
| `DX402_STORE_BACKEND` | `s3` | `s3` \| `ipfs` \| `arweave` (only `s3` in v0.1) |
| `DX402_STORE_BUCKET` | *(unset)* | required for `s3` |
| `DX402_STORE_PUBLIC_BASE` | *(unset)* | public base URL a pointer dereferences through |
| `DX402_REGISTRY_TABLE_NAME` | *(unset)* | DynamoDB index; unset falls back to memory |
| `DX402_SIGNING_KEY` | *(unset)* | receipt signing key; Secrets Manager in production |
| `DX402_RETENTION` | `90d` | `90d` \| `1y` \| `permanent` |
| `DX402_REQUIRE_PROOF` | `false` | **Phase 1**: the anchor gate verifies and reports without rejecting. Flip to `true` only once the logs show real traffic passing |
| `DX402_ANCHOR_MAX_AGE_SECS` | `900` | How old a payment may be when its evidence is anchored |

Missing configuration **disables** the feature and logs why. It never falls back
to something that merely looks durable — an in-memory "durable" store in
production would report evidence for data that dies with the process.

## Endpoints

| Method | Path | Purpose |
|---|---|---|
| `POST` | `/dx402/anchor` | a resource server reports an anchor |
| `GET` | `/dx402/evidence/{paymentId}` | pointer, hash, mode, receipt |
| `GET` | `/dx402/receipt/{paymentId}` | signed receipt, verifiable offline |
| `GET` | `/dx402/blob/{paymentId}` | the sealed ciphertext itself |
| `GET` | `/dx402/stats` | how much evidence has been notarised |
| `POST` | `/dx402/repair/{paymentId}` | **admin only** — audit one anchor, and with `?write=true` correct a pointer that names nothing |
| `POST` | `/dx402/recover` | `escrowed` mode — **501 in v0.1** |

`/dx402/blob/{paymentId}` is **unauthenticated on purpose**: in `direct` mode the
bytes are sealed to the payer's own public key, so serving them to anyone reveals
nothing. That is what lets the evidence bucket stay private with no public read
path at all — the access control lives in the cryptography rather than in an ACL
that could be misconfigured.

`/dx402/recover` returns an honest `501`. `direct` mode needs no recovery
endpoint at all: the buyer already holds the only key that opens the payload.

### Error codes

`dx402_disabled`, `dx402_unknown_payment`, `dx402_not_payer`,
`dx402_challenge_expired`, `dx402_challenge_replayed`, `dx402_direct_mode`,
`dx402_evidence_expired`, `dx402_store_unavailable`, `dx402_proof_rejected`
(402), `dx402_already_anchored` (409), `dx402_signature_not_verified` (422),
`dx402_backend_unavailable` (422).

**409 and 422 are not the same failure.** Both mean an existing record kept your
anchor out, but only 422 tells you why it could not supersede it: you sent a
`sellerSignature` and it did not verify against the payee. The distinction
matters more than it looks. `dx402_already_anchored` is *true* in both cases, and
it is a plausible story — the reader goes off to audit retries, races and
repeated heartbeats, and finds candidates, because those always exist. Nobody
suspects the shape of a digest they do not know has shapes. Reported by
KarmaKadabra, 2026-08-19, after isolating it with three anchors to one paymentId.

A rejected signature does **not** cost you the anchor when nothing else holds the
slot: the record still lands, provisionally, so a seller-side signing bug never
costs the buyer its copy. The `verified` field on the `201` is where you see it.

### `verified`: the difference between evidence and a claim

`POST /dx402/anchor` and `GET /dx402/evidence/{paymentId}` both return
`verified`. It is `true` only when the payee proved by signature that the anchor
is theirs.

Treating a provisional record as proof of *who produced the artifact* is trusting
something anyone could have written. Provisional still means the bytes are real
and decrypt — the `contentHash` check is independent — it only means nobody
proved where they came from.

### Size limit

`POST /dx402/anchor` accepts at most **64 KiB of request body**
(`MAX_REQUEST_BODY_BYTES`, an anti-OOM bound on every route, not a DX402 rule).
When you send the blob inline as `sealed`, it travels base64 (4/3 inflation) plus
metadata, which leaves a band of roughly **48.1–48.7 KB of plaintext** — the
band moves because the metadata does: minimal is ~456 bytes, and it passes 1.3 KB
once `sellerSignature` and `proofOfPayment` are present. The boundary is the request limit
itself, and there is no DX402-specific error for crossing it: v2.3.0 added one
and v2.7.0 removed it, because a cap on the decoded blob cannot be right at any
value. `RequestBodyLimitLayer` is the outermost layer on the router, so anything
over 64 KiB is cut before a handler runs. A blob cap below what the request
limit allows refuses bodies that used to anchor — 48,000 rejected everything up
to 48,810 — and one above it is unreachable. An oversized anchor gets a bare
`413`, and that cannot be improved from inside the handler.

**Measure the cut on the sealed request, not on the plaintext.** The envelope
adds a nonce, the wrapped CEK and its JSON; checking the plaintext lets through
bodies the facilitator then rejects, and the failure arrives long after the
sealing work was done. Both SDKs now check the serialised request and return
`{"skipped": "too_large"}` before touching the network.

This limit binds only for inline `sealed`. A seller that uploads to its own
storage and sends a `pointer` has no size ceiling — which is what the Rust
`x402-axum` hook does, so it is unaffected. **Raising `DX402_MAX_BODY_BYTES` does
not raise this one**: they bound different things, one the seller's memory and
one the facilitator's request body.

### Pinata: what the dashboard counter does NOT count

Measured 2026-09-01 against the live account.

| | |
|---|---|
| Plan | **Free** ($0/month) |
| Dashboard "Files" | **3 / 500** |
| Dashboard "Storage" | **3.90 KB / 1 GB** |
| Requests | 508 / 10 K |
| **Private files DX402 actually wrote** | **481, totalling 1.40 MiB** |
| JWT expiry | **2026-12-19** |

**Those 481 do not appear in the dashboard's 3/500.** The counter reports public
IPFS pins; DX402 writes to the v3 *private* files API, and the two are separate.
Anyone reading `Files 3/500` and concluding there is room, or reading a private
file count and concluding the quota is nearly gone, is comparing numbers that do
not govern each other. This document had the second error first: 481 was read
off the private API and set against the 500-pin public quota, producing a "19
files of margin" alarm that was never real.

No quota for private files is displayed anywhere, and no endpoint reachable with
the scoped JWT reports one — `v3/user`, `v3/account`, `v3/user/plan` and
`v3/files/private/usage` all 404, and `users/me` answers 403. So the private
ceiling is **unknown**, not unlimited. What can be said: at ~3 KB per sealed
anchor, 1 GB is roughly 350,000 anchors, and the store held 562 on the day this
was measured.

**Nothing needs upgrading.** What needs watching is the JWT, whose expiry makes
every anchor fall back to S3 with no error anywhere — see the
`dx402-store-fallback` alarm in `terraform/environments/production/alerts.tf`,
which fires on that, on quota exhaustion, and on any Pinata outage, because all
three arrive through the same door.

### The anchor gate

Every anchor is checked against the chain: the payment is real and succeeded,
**the payer is the address the evidence was sealed to**, and **the payee signed
the anchor**. One payment anchors once.

Two verdicts never block, in either phase. `dx402_rpc_unavailable` means no
verdict was reached — our outage must not be recorded as somebody's anchor being
fraudulent. `dx402_unverifiable_chain` is the non-EVM case: there is no receipt
to read, and enforcing a check that never ran would silently disable DX402 on
Solana, NEAR, Stellar and Algorand.

Sellers supply `proofOfPayment` (straight from the settle response) and
`sellerSignature`. In `x402-axum`, `with_anchor_signer()` handles the second.

### Letting the buyer choose: two offers in `accepts`

Evidence costs the seller memory and storage, so it should be the buyer's call.
x402 already returns an **array** of offers in the 402; the opt-in uses nothing
else. The seller lists the same resource twice, plain and with the extension,
priced separately:

```rust
let x402 = X402Middleware::try_from(facilitator)?
    .with_price_tag(usdc.amount(0.010).pay_to(seller))                 // plain
    .with_durable_offer(usdc.amount(0.012).pay_to(seller),             // + evidence
        DurableEvidenceConfig { retention: Retention::Year1, ..Default::default() })
    .with_durable_evidence(hook);
```

The buyer side is one call: `X402Payments::with_wallet(w).prefer_durable_evidence()`.
A client that never asks keeps paying for the plain offer — **regardless of the
order the seller listed them in** — which is what makes this proposable: nothing
in the x402 core changes, and old clients degrade to exactly what they had.

What the hook does with the paid offer (`OfferDecision` in `x402-axum`):

| Route offers evidence? | Buyer paid the offer with it? | Result |
|---|---|---|
| yes | yes | anchored on **that offer's** `retention`/`mode` |
| yes | no | delivered, header `{"skipped":"not_selected"}` |
| no | — | anchored on the route config — everyone who attached the hook before offers existed is unchanged |

The declaration lives at `extra.extensions["durable-evidence"]` on a v1
requirement (mirroring v2's top-level `extensions`), read and written through
`DurableEvidenceConfig::{from_requirements, declare_on}` so the two sides cannot
drift. A malformed declaration reads as "not declared", never as an error.

### Payments released from an x402r escrow

On the escrow rail the ERC-20 `from` is the operator's **TokenStore**, not the
buyer, so "the evidence must be sealed to whoever paid" cannot be answered from
the `Transfer` alone. Measured 2026-09-02: 23 of 23 sampled live Execution
Market releases reported a payer that was not the buyer.

Those anchors carry `escrowRelease` as well:

```jsonc
{
  "escrowRelease": {
    "paymentInfo": {          // the authorization, exactly as the escrow hashes it
      "operator": "0xC2377a9D…", "receiver": "0xf16F0882…", "token": "0x0b2C639c…",
      "maxAmount": "20000",   // a string; uint120 does not fit a JSON number
      "preApprovalExpiry": 1788153221, "authorizationExpiry": 1788757421,
      "refundExpiry": 1789362221, "minFeeBps": 0, "maxFeeBps": 1800,
      "feeReceiver": "0xC2377a9D…", "salt": "0x8a4644fd…"
    },
    "payer": "0x7Fd9F9E5…"    // the buyer who funded the escrow
  }
}
```

Nothing here is taken on trust. The facilitator asks the escrow to `getHash` the
authorization and requires the answer to be a `paymentInfoHash` **that same
transaction** captured, so an edited field — `payer` above all — changes the hash
and the anchor is refused with `dx402_escrow_release_invalid`. Omitting the field
on an escrow payment gives `dx402_escrow_release_missing`, which is a different
answer from `dx402_payer_is_not_recipient` on purpose: one is a field you forgot,
the other is an accusation.

A transaction that settles **more than one** escrow payment answers
`dx402_escrow_release_ambiguous` and is never certified. `paymentId` is
`keccak256(caip2 || txHash)`, so batched payments collide on it, and certifying
either would be a guess whose losing side is a stranger's delivery.

**Who signs.** The payee of the release signs — on a marketplace that is the
seller who got paid, not the platform that brokered it. Execution Market anchors
provisionally because it is neither payer nor payee; the worker supersedes it
with a signed anchor. The 900-second freshness window applies to that supersede
too, so it has to arrive promptly.

Only `dx402_store_unavailable` carries `"retryable": true`. **Do not persist a
retryable failure as a permanent "no evidence" answer** — that is how INC-2026-07-21
turned a transient RPC failure into a permanent wrong answer.

`404` (never existed) and `410` (expired) are deliberately different: they are
different answers to a dispute.

## Security notes

1. **Anchoring is publishing.** `retention: permanent` is irrevocable. The
   default is bounded (90 days) so that one careless anchor of PII is not
   unfixable.
2. **Harvest-now-decrypt-later.** ECDH over secp256k1 is not post-quantum. Do not
   anchor permanently what must not survive.
3. **`escrowed` centralises risk** and must be declared in the receipt so no
   verifier confuses its guarantee with `direct`.
4. **Small-order keys are rejected.** `ed25519-dalek` accepts non-canonical and
   small-order encodings in `VerifyingKey::from_bytes`; unchecked, that would
   collapse the ECDH shared secret to a constant. Rejected in constant time per
   RFC 7748 §6.1, tested against libsodium's blacklist.
5. **Cache leakage is mitigated as a side effect.** Attack III of the referenced
   paper measured 100% leakage of paid responses through an nginx cache. A body
   encrypted to the payer is useless to an intermediary that caches it.

| Extension | Proves |
