# CI path filters: what triggers the pipeline, and what no longer does

**Date:** 2026-09-11
**Change:** `paths` on `.github/workflows/ci.yaml`, plus `cancel-in-progress` for
pull-request runs. `no-account-id.yml` deliberately untouched.
**Verified by:** `python3 scripts/ci_paths_selftest.py` (88 assertions), `actionlint`.

## Why

`ci.yaml` triggered on any push and any pull request, with no path filter. In the
24 h to 2026-09-11 it produced 36 runs and 392 wall-minutes:

| Bucket | Runs | Wall-min | Share |
|---|---:|---:|---:|
| Runs whose entire diff was documentation | 2 | 35.6 | 9.1% |
| Pull-request runs overtaken by a newer push to the same branch | 8 | 54.3 | 13.8% |
| Runs that touched only infrastructure, no image input | 6 | 65.7 | 16.8% |
| Everything else | 20 | 236.6 | 60.3% |

A push run costs ~16 min (test ~6.5, plan ~0.7, deploy ~9.5); a pull-request run
costs ~7 min, since `deploy` is skipped. `no-account-id.yml` costs ~10 s per run,
6 min across the same 36 runs — 1.5% of the budget.

This change addresses the first two buckets, 89.9 min or 22.9%. The third is
analysed below and deliberately left alone.

## Job → the paths it reads

Measured by reading each job's steps, the `Dockerfile`, and the one script the
pipeline invokes. GitHub has no per-job `paths`, so the workflow-level list is
the union of this table.

| Job | `needs` / `if` | Reads |
|---|---|---|
| `test` | — | `src/**`, `crates/**`, `examples/**`, `tests/**`, `abi/**`, `config/**`, `static/**`, `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `.cargo/**`, `scripts/verify_landing_canonical.py` |
| `preflight` | — | nothing. It reads two repository secrets and writes `deploy=true/false`. No checkout. |
| `plan` (drift gate) | `needs: [preflight]`, `if: deploy == 'true'` | `terraform/**`, and `.github/workflows/ci.yaml` itself — it greps this file for `-target=` flags so the gate and the deploy cannot drift apart |
| `deploy` | `needs: [test, preflight]`, `if: deploy == 'true' && ref == main && (push \|\| workflow_dispatch)` | everything `test` reads, plus `Dockerfile`, `.dockerignore`, `VERSION`, `terraform/**`, `lambda/**` |

Four of those entries are not obvious and were each confirmed in the source
rather than assumed:

- **`static/**` is a build input, not an asset directory.** `src/handlers.rs`
  carries roughly forty `include_str!` / `include_bytes!` sites over `static/`,
  the landing page among them. The Dockerfile even fails the build when the
  string `Ultravioleta` is missing from the compiled binary. A change to the
  landing page is a change to the binary, so it takes the full build.
- **`abi/**` is compile-time.** Alloy's `sol!` macro reads those JSON files at
  macro expansion in `src/chain/evm.rs`, `src/escrow.rs`, `src/upto/abi.rs` and
  `src/payment_operator/abi.rs`.
- **`config/**` is both.** `src/discovery_curation.rs` compiles one manifest in
  with `include_str!`, and the runtime image copies the whole directory to
  `/app/config`.
- **`tests/**` holds real Rust integration tests** (`tests/wire_conformance.rs`
  and seven siblings), with `tests/fixtures/` and `tests/vectors/` feeding them.

## What now triggers what

| A commit touching… | `ci.yaml` | `no-account-id.yml` |
|---|---|---|
| `docs/**`, `README.md`, `CLAUDE.md`, `guides/**`, `.claude/**` | nothing | scans (PR and push) |
| `scripts/bench/**`, any operator script except the landing checker | nothing | scans |
| `docker-compose*.yml`, `justfile`, `.editorconfig` | nothing | scans |
| `static/**` (the landing page, logos, stylesheets, fonts) | build + test + deploy | scans |
| `src/**`, `crates/**`, `examples/**`, `tests/**`, `abi/**`, `config/**` | build + test + deploy | scans |
| `Cargo.*`, `rust-toolchain.toml`, `.cargo/**`, `Dockerfile`, `.dockerignore`, `VERSION` | build + test + deploy | scans |
| `terraform/**` | build + test + plan + deploy | scans |
| `lambda/**` | build + test + deploy (the balances-Lambda apply step fires) | scans |
| `.github/workflows/ci.yaml` | build + test + plan + deploy | scans |

`workflow_dispatch` has no `paths`. A manual "Run workflow" on main still
deploys, re-applies the Lambda, re-runs the drift gate and re-enables the
discovery bucket's versioning, whatever the last commit changed. That is the
escape hatch if a filter ever turns out to be too narrow.

## There is no landing-only shortcut here, and that is the point

The obvious win — a portada change publishing only the portada — does not exist
in this repository. Other projects sync a landing page to S3 and then fix
`Content-Type` in a second step, which is where a path filter can reorder or
drop half the work. This facilitator serves its landing page from inside its own
binary. `grep -n 'aws s3' .github/workflows/ci.yaml` returns exactly one line,
a read-only `get-bucket-versioning`. There is nothing to sync and nothing to
split, so `static/**` sits in the union with the Rust sources and a landing
change pays for a full build. That is correct, not a missed optimisation.

## The infra-only bucket: measured, and left alone

Six runs, 65.7 wall-min, changed only `terraform/**` and prose. Each paid a full
`cargo build` plus an image build to ship an image whose binary was byte-identical
to the one already running. It is the largest single bucket and the tempting next
step, and it is where this change stops, for one concrete reason:

`deploy` tags its image `$(cat VERSION)-$(git rev-parse --short HEAD)` and then
passes that tag to `terraform apply -var="image_tag=…"`. Any job graph that skips
the image build for an infra-only commit points the ECS task definition at a tag
that was never pushed to ECR. Fixing that means resolving the tag from what is
already live, which is a change to the release path itself.

Skipping just the `test` job is not cheaper either: `deploy` lists `test` in
`needs`, so a skipped `test` skips `deploy` unless the condition is loosened to
`always()` — and a deploy that can run with `always()` is a deploy that can ship
untested code. Both are real changes to how a release works and belong in their
own pull request, with their own verification.

## `no-account-id.yml` is unfiltered on purpose

It scans every tracked file for an ARN carrying an account, an ECR registry host
and a Secrets Manager suffix; and it scans `*.md` plus `.claude/` for a bare
12-digit number. That last rule's only target is prose, which is exactly the
class of change a documentation filter would exclude. The repository is public
and `main` carries no branch protection, so a direct push is possible and the
pull-request run is not a complete substitute for the push run.

At ~10 s a run, 6 min across 24 h, the check costs 1.5% of the budget and is the
only gate that reads documentation. Filtering it would trade that for nothing
worth having. `scripts/ci_paths_selftest.py` asserts it stays unfiltered, so
narrowing it later has to be a deliberate edit to that file rather than a
side effect.

## Verifying a change to the filter

```bash
python3 scripts/ci_paths_selftest.py
```

It reimplements GitHub's glob rules — `**` crosses `/`, `*` does not, which is
where `fnmatch` disagrees and would confirm a wrong filter — and then asserts:

1. Every build input above is matched, and every documentation path is matched
   by nothing.
2. `push` and `pull_request` carry byte-identical `paths` lists. GitHub Actions
   has no YAML anchors, so the list is written twice; this is the only thing
   keeping the two copies together.
3. Every pattern matches at least one tracked file. A typo such as `lambdas/**`
   is invisible to the cases above — it simply never matches, and the job it was
   meant to guard quietly stops running.
4. `no-account-id.yml` still triggers on documentation.

## Also in this change (its own commit, droppable on its own)

`concurrency.cancel-in-progress` is now `${{ github.event_name == 'pull_request' }}`
instead of a flat `false`. Pushing twice to a pull-request branch left the first
run compiling for another six minutes with nobody waiting on its answer; that was
54 of the 392 wall-minutes. The group key is `github.ref`, so a push to main never
shares a group with a pull request and still evaluates to `false` — two releases
queued back to back must both run, since cancelling the first would stop it
between `terraform apply` and the rollout wait. The `deploy` job's own
`deploy-production` group is the second guard.
